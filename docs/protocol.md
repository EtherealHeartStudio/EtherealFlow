# CherryVoice 流式识别协议 v1

与需求文档 §7.1 一致，并记录本项目对原始规范的**两处扩展**（不影响只实现原规范的客户端）。

* 传输：WebSocket
* 默认地址：`ws://127.0.0.1:18300`（服务端默认监听 `0.0.0.0:18300`，WSL2 localhost 转发到 Windows）
* 音频格式：**16 kHz / 单声道 / 16-bit PCM（小端，裸二进制帧，无容器头）**
* 帧边界不等于语义边界：服务端内部按 `chunk_ms`（默认 160 ms）重新切块，客户端可以发任意大小的块

## 客户端 → 服务端

| 帧 | 内容 | 说明 |
|---|---|---|
| 二进制帧 | 原始 PCM int16 LE | 建议 160 ms = 2560 采样 = 5120 字节 |
| 文本帧 | `{"type":"start","language":"Chinese","context":"热词"}` | 可省略；省略时服务端在第一帧音频到达时按默认参数自动开会话 |
| 文本帧 | `{"type":"finish"}` | 音频结束，请求最终结果 |
| 文本帧 | `{"type":"cancel"}` | **扩展**：丢弃本次会话，不返回结果（对应 Esc 取消） |
| 文本帧 | `{"type":"ping"}` | **扩展**：探活，服务端回 `{"type":"pong"}` |

`language`：`null`/省略 = 自动检测；也可传 `"Chinese"` / `"English"` 等（见模型支持列表）。
`context`：热词/上下文提示，直接作为识别引擎的 `context` 参数。

## 服务端 → 客户端

| 帧 | 内容 |
|---|---|
| `{"type":"ready","model":"confucius4-r2t2","sample_rate":16000,"chunk_ms":160,"protocol":1}` | **扩展**：连接建立后立即下发，客户端据此判断服务可用 |
| `{"type":"started","language":...,"context":...}` | **扩展**：收到 `start` 后的确认 |
| `{"type":"partial","text":"舰长，升级 https 之后"}` | 累积全文，**有变化才发** |
| `{"type":"final","text":"...","duration":6.74,"chunks":42,"decode_ms":3915.5,"max_decode_ms":337.5,"wall_ms":6880.8}` | `duration` 起的字段为**扩展**，便于性能观测 |
| `{"type":"error","message":"..."}` | 协议错误等 |
| `{"type":"cancelled"}` | **扩展**：`cancel` 的回应 |

### 客户端必须处理的三种情况

1. **`partial` 是累积全文，不是增量** —— 客户端每次直接替换显示内容，不要自己拼接。
   这样后端偶发的少量回滚（rollback）天然被覆盖，UI 不会错位。
2. **空文本的 `partial` 不会下发**。后端在还没有解析出 `<asr_text>` 标签时会短暂把结果清空，
   这是**正常的中间态**；服务端已过滤，并且 `final` 为空时会回退到最后一个非空 `partial`。
   客户端不要因为收到空串就清屏。
3. **`final` 可能等于最后一个 `partial`**。别把两者不同当作异常。

## 会话与并发

* 每个连接维护一个独立的 `streaming_state`，一个连接同时只有一个会话。
* 收到新的 `start` 会**丢弃**当前未完成的会话并重开。
* GPU 推理用全局锁串行化：多个连接可以并存，但同一时刻只有一个在解码。
  单用户场景（一个输入法）不受影响。

## 音频块大小与首块策略

* 服务端内部固定按 `R2T2_CHUNK_MS`（默认 160）切块解码。
* 第一块会多等一个 `R2T2_FIRST_LOOKAHEAD_MS`（默认 160）的 lookahead，
  与官方 `example.py` 的 `run_streaming()` 首块策略一致（首块上下文更足，首字更准）。
  设为 `0` 可让首块立即解码（首字最多提前 160 ms，实测对本机测试音频无差别）。

## 性能特征（实测，本机 RTX 4070 Laptop 8 GB）

流式解码的成本随音频长度增长（每块都要重新编码累积音频，接近 O(n²)）。
以下全部是**同一份音频重复拼接**后的实测值：

| 音频长度 | 总解码耗时 | 折合实时 | 单块最慢 |
|---|---|---|---|
| 6.74 s（42 块） | 3.6–3.9 s | 0.53–0.58× | 228–549 ms |
| 20.22 s（126 块） | 14.5 s | 0.72× | 364 ms |
| 33.70 s（210 块） | 29.6 s | 0.88× | 288 ms |
| **53.92 s（337 块）** | **62.2 s** | **1.15×** | 623 ms |

* `< 1.0×` 表示比实时快，边说边识别不会积压；**`> 1.0×` 就跟不上说话了**。
* 拐点在 **~45 秒**附近。需求文档 风险 #3 说"说话超过 30 秒时，考虑分段重建会话"，
  实测证实了这条 —— 而且给出了具体的数字。
* 一次性整段识别（`LlamaNativeOnetime.generate_once()`）不受此影响，
  6.74 s 音频约 0.5 s 完成 —— 所以**不要把整段音频丢进流式循环**。

### 客户端的分段重建（已实现）

客户端默认在**连续说话 30 秒**（`asr.max_utterance_sec`）时主动
「结束当前段 → 拿到 final → 累积到前缀 → 立刻开新的一段」，对用户是无感的：
悬浮窗上文字照常增长，只是内部换了一次 `streaming_state`。

同一份 33.70 s 音频，把分段上限设成 8 s 实测：

| | 单会话 33.7 s | 分段（每段 8 s） |
|---|---|---|
| 解码/秒 | 0.88× | **0.54×** |
| 单块最慢 | 288 ms | **162 ms** |
| 段内块数 | 210 | 50 |

代价是**段与段之间可能出现轻微的接缝**（切点可能落在一个词中间），
所以上限不能设得太小：8 s 是测试值，默认 30 s 更稳妥。

## 长连接与背压

* 服务端默认 keepalive 是 `ping 20 s / ping timeout 60 s`。
  这里**故意把超时放宽**：长语音时客户端可能因为服务端处理不过来而在
  `sendall` 里阻塞几十秒、一时顾不上回 pong，20 s 的默认超时会把这种**正常背压**
  误判成死连接并断开（实测 53.9 s 音频就是这样被打断的，报 1011）。
* 客户端每轮最多连发 8 帧就回去收一次，保证不会长时间不回 pong。
