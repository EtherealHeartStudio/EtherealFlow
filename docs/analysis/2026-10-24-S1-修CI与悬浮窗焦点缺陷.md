## 2. 怎么验证的

### 2.1 CI 的 cp1252 崩溃 —— 本地复现过

```bash
python -c "import sys, io; sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding='cp1252'); print('将运行 11 个测试')"
# → UnicodeEncodeError: 'charmap' codec can't encode characters
```

这正是 GitHub Actions Windows runner 的情况（stdout 编码 cp1252）。
两层防护都装了：进程级（`import _utf8`）+ 环境级（CI 的 `PYTHONUTF8: 1`）。

### 2.2 BF-15 悬浮窗抢焦点 —— 四层根因逐个复现

| 根因 | 复现方式 | 证据 |
|---|---|---|
| `GA_ROOT` 在 `overrideredirect` 后失效 | 枚举进程所有顶层窗口 | `top_level_window` 返回 TkChild，真正的 TkTopLevel 是**兄弟**不是父级 |
| NOACTIVATE 加得太晚 | `tools/repro/overlay_focus_timing.py` 三组对照 | 「现状」抢焦点 ✅，「提前加样式」不抢 ✅ |
| `-topmost` 触发重新激活 | 五组属性组合对照 | 去掉 `-topmost` 即不抢 |
| `ShowWindow` 排在 `SetWindowPos` 前面 | 顺序对照 | `ShowWindow→SetWindowPos` 抢；`SetWindowPos→ShowWindow` 不抢 |

**最终证据 —— 完整闭环打通**：

## 4. 遇到的问题

1. **「悬浮窗不抢焦点」的原有保证其实是假的。**
   `client/overlay.py` 的注释写着「真正会被激活的是顶层窗口」，
   `docs/architecture.md` §4.1 也专门讲了这个坑 —— 但 `top_level_window()`
   用的 `GA_ROOT` 在 `overrideredirect` 之后**恰好失效**，
   于是样式加回了子窗口，`has_noactivate()` 自欺欺人地返回 True。
   **文档写对了，代码没做对。**

2. **Windows 首次映射窗口必然激活它，且有随机性。**
   同样代码连跑，有时抢有时不抢。这让「靠 NOACTIVATE 挡住」不可靠，
   必须叠加「显示前记焦点、显示后还回去」的兜底。

3. **跨线程还焦点在本机做不到。**
   `AttachThreadInput` 关联 Chrome 的 UI 线程返回 0（失败）。
   所以「还焦点」只能是尽力而为 —— 真正的修复必须是**一开始就不抢**。

4. **BF-15 是靠「把 CI 修好 + 把闭环测试加进套件」才暴露的。**
   这两个测试从 v0.1.0 起就存在，但**从未在 CI 里跑过**。
   缺陷一直躺在那儿，只是没人跑它。
