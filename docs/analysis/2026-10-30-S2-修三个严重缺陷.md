## 1. BF-1 长语音分段丢内容（严重）

### 症状

说超过 30 秒，中间丢一段。真实 WSL 服务实测：对照组 34 字 → 轮转组 23 字，**丢 32%**。

### 根因（四层，逐个修）

| # | 原因 | 修法 |
|---|---|---|
| 1 | 轮转时 `feed()` 照常把音频发给**正在收尾的旧会话** | 客户端加暂存区 `_audio_hold`，轮转期间扣住，新会话 `start` 发出后再放行 |
| 2 | 服务端 finish 之后收到音频会**按默认参数自动开新会话**（丢掉 language/context） | 服务端加 `accepting` 标志：finish/cancel 之后不再自动开会话，音频计数丢弃 |
| 3 | 客户端重开会话发的 `start` 会**丢弃**那个自动会话 → 那段文本永远进不了 final | 服务端兜底：`start` 时若旧会话**真有内容**，先 flush 出 final 再丢（空会话不 flush） |
| 4 | **松手恰好在轮转途中**时，新会话开起来后**没人给它发 finish** → 新会话永远等不到 final，最后一段整个消失 | `end_session` 记 `_end_pending`；`begin_session` 释放 hold 后若发现「用户已松手」，补发 finish |

### 验证

```
$ .venv/Scripts/python.exe tools/test_rotate_no_loss.py
对照组字数 : 34
轮转组字数 : 34
差值       : 0 字（0%）
[PASS] 轮转未丢内容（差值 ≤ 1 字）
```

**双向验证**：只修服务端时（`git stash` 掉客户端改动）→ 丢 22 字（65%），用例正确报 FAIL。

> ⚠️ 用例走**真实 `AsrClient`**，不是裸 WebSocket。
> 裸协议客户端不扣音频，测不到客户端这一侧的修复 —— 这是我一开始写错的地方。

## 2. BF-3 Esc 取消是死代码（严重）

### 症状

需求文档 FR-1 写着「录音中按 Esc 取消本次输入」。实际这个功能**根本不存在** ——
按 Esc 什么都不会发生，松手照常注入。

### 根因

`client/hotkey.py` 的 `active` 字段**从来没被设成 True**（只有 `tools/test_hotkey.py`
手工设过）。两个后端的 Esc 分支都要求 `self.active` 为真 → `on_cancel` 在生产中永不触发。

### 修法

`active` 的语义统一为「当前正在录音」，由热键的**按下/松开**驱动：

- `PollingHotkey._run`：按下时 `active = True`，松开时 `active = False`
- `HookHotkey._callback`：组合键成立时 `True`，解除时 `False`

顺带修的：
- `app._on_cancel` 现在会清掉 `_prefix` / `final_text`（取消 = 当没说过）
- 客户端 `_pump` 现在处理服务端的 `cancelled` 帧（之前不处理 → `session_open` 卡在 True，
  下次按热键会被「已在录音中」挡掉）

### 验证

```
[PASS] 热键层：按下后 active=True，Esc 边沿触发 cancel
        active(按下后)=True 事件序列=['press', 'cancel', 'release']
[PASS] 应用层：取消后不注入任何文字
        session_active=False final_text='' 前缀='' 目标框内容=''
```

**双向验证**：修复前 `active=False`、事件序列 `['press','release']`（无 cancel）。

## 4. 顺带发现并修掉的两个问题

### 4.1 「两个 start」——一个既有 bug，被我加的服务端兜底暴露了

加完服务端的「start 时先 flush 旧会话」后，闭环测试立刻挂了：
`FINAL: duration 0.0, chunks 0`。

**根因**（既有 bug，v0.3.0 就有）：连接建立要十几毫秒，这期间用户按下热键，
`begin_session` 往队列塞了一个 start；连接一建立，`_run` 里**又补发**一个
→ 两个 start → 服务端收到第二个就「重开会话并丢弃旧会话」，刚到的音频全废。

**修法**：
- 客户端：连接建立时先 `_drop_pending_starts()` 清掉队列里残留的 start，再补发一个
- 服务端：只在旧会话**真有内容**（`duration > 0 or chunks > 0`）时才 flush
  —— 空会话 flush 出来是空 final，客户端会当成「这段说完了」而提前结束

> 这个 bug 之前没暴露，是因为服务端原来只是「静默丢弃」旧会话，不发 final。
> 我的服务端改动让它显形了 —— 算是自己踩自己。

### 4.2 「测试连接」只看模型列表，会给出假的绿灯

今天代理端所有模型都 `auth_unavailable`（配额用尽），但 `gpt-5.6-sol`
**仍然列在 `/v1/models` 里** —— 于是设置界面显示「✓ 连通」，用户一用就失败。

**修法**：`test_connection()` 现在**真的发一次最小请求**（8 token）。
设置界面的「测试连接」按钮从此反映**真实可用性**。

顺带把 `test_llm_live.py` 的行为修正了：端点配额用尽时，
它现在报 **SKIP**（环境依赖）而不是 16 条断言全挂（看起来像代码回归）。
这与 S1 建立的「区分环境做不到与代码错了」的规矩一致。

## 6. 遇到的问题

1. **回归用例一开始写错了**：用的是裸 WebSocket 协议，测不到客户端的暂存区逻辑。
   改成走真实 `AsrClient` 才有意义。
2. **「松手恰在轮转途中」是独立于「轮转丢字」的第二个 bug**，
   表现是最后一段整个消失。第一次只修了音频扣留，还会丢。
3. **自己的服务端改动暴露了自己的另一个 bug**（两个 start）。
   这说明「加防御性代码」会改变系统的行为边界 —— 必须配套全量回归。
4. **LLM 端点今天配额用尽**（`usage_limit_reached`），
   导致 `test_llm_live.py` 16 条断言全挂。**这不是代码回归** ——
   用 `git stash` 对照验证过：未改动的代码跑同一个测试也是 16/16 失败。
   但它暴露了测试设计的缺陷（环境问题被报成断言失败），已修。
