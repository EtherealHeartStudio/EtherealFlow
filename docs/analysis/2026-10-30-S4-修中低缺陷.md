## 二、这一阶段里被证伪的「已完成」

这一阶段最有价值的产出不是新功能，而是**推翻了几条「文档写了但其实没做」的说法**。

### 2.1 「麦克风尾块没丢」—— 其实每次都丢

`MicCapture.flush()` 定义了但**全仓没有调用者**。麦克风按 160 ms 一块切分，
用户松手时缓冲区里往往还剩**不足一块**的尾巴 —— 不吐出去就等于每次都丢掉最后那点音（实测最多 160 ms）。

**修法**：`MicCapture.stop()` 在 worker 退出**之后**调 `flush()`
（退出后再 flush：那时不会有新数据进来，也不存在与 worker 争抢 `_buf` 的问题）。

### 2.2 「设备是可选的」—— 其实只能手改配置文件

`client/settings_ui.py` 里 `list_input_devices` **导入了但没用**。
需求 FR-2 写着「设备可选（设置里列出输入设备）」，实现里没有。

更麻烦的是：**序号会漂移**。插拔一次 USB 声卡、换个蓝牙耳机，
同一个物理麦克风的序号就可能变 —— EtherealLive 的 P9 计划里明确记了这个坑
（「同一支麦在重启后换了序号」）。只存序号 → 用户昨天还好好的麦今天「没了」。

**修法**：
- 配置里**同时**存 `device`（序号）与 `device_name`（名称）
- 启动时 `resolve_input_device()`：**按名优先、序号兜底**
- 名称匹配不要求完全相等 —— 不同机器上报的名字会**重排词序**
  （`"Realtek Microphone"` vs `"Microphone (Realtek Audio)"` 互相都不是子串），
  所以改成**词集合包含**判定
- 词集合判定要求**包含**而不是只要有交集 —— 否则 `"USB Mic"` 会和 `"USB Speaker"`
  误判成同一个设备（认错了就把录音采到扬声器上）

### 2.3 「设置改完要重启」—— 现在不用了

`App.__init__` 里 LLM 客户端构造一次就再没动过 → 改模型名 / 改 Prompt 要重启整个程序。

**修法**：新增 `client/hotreload.py`。客户端**盯着配置文件**，发现变了就重新加载，
把能热更新的部分立刻换掉：

| 配置 | 能否热更新 | 说明 |
|---|---|---|
| `llm.*` | ✅ | 重建 LLM 客户端 |
| `translate.*` | ✅ | 下一次说话时用新参数 |
| `inject.*` | ✅ | 重建注入器 |
| `hotwords` | ✅ | 下一次开会话就带上 |
| `asr.*` | ✅ | 地址变了要重连识别服务 |
| `audio.*` | ✅ | 下一次开麦时用 |
| `hotkey.*` | ❌ | 热键线程要重建，会打断正在进行的输入 |
| `overlay.*` | ❌ | 悬浮窗是 Tk 窗口，重建会闪 |

「不能热更新」的部分**必须在界面上写清楚**，否则用户改完发现没反应会以为程序坏了 ——
所以设置窗口底部常驻一段说明，保存后的对话框里也再写一遍。

**「保留一次连接预热」是什么意思**：`LlmClient` 用 `urllib` 发请求，**没有长连接**，
没什么连接池可保。真正要保的是**重建时正在飞行中的请求不能被打断** ——
所以新客户端建好之后才把旧的换掉（换的过程是原子的）。

### 2.4 写热更新时踩到的两个真 bug

**（1）`ConfigWatcher.poll()` 的竞态** —— 回调被吞掉。

原来的实现先更新 `_last_mtime`、**再**读文件、**再**回调。
监视线程和外部调用可能同时进来：一个线程更新了 `_last_mtime` 但回调还没跑，
另一个线程就看到「没变化」直接返回 —— 回调于是被**吞掉**（实测：文件改了但回调一次都没发生）。

而且更糟：读文件失败（比如设置界面 `write_text` 写文件时正好落进
「先截断、再写」的窗口，读到半个文件）时**照样更新了 mtime** ——
这次改动就**永远丢了**，用户改了设置却没生效，而且再也等不到。

**修法**：整个过程在一把锁里；**读失败就不更新 mtime**，下一轮重试。

**（2）设备名「词序变化」认不出** —— 子串匹配不够用。

见 2.2。

## 三、FR-3 补齐：电平条与 error 状态

### 3.1 音量电平条（FR-3.5）

`MicCapture.peak` 算了但没人读 —— 悬浮窗里没有任何音量指示。
用户不知道麦克风到底有没有收到声音（静音、选错设备都表现为「按了热键没反应」）。

**数据通路**：`app._on_audio_block()` → `overlay.set_volume(peak)` → 主线程画 Canvas。

**踩到的坑（按帧衰减 ≠ 按时间衰减）**：

第一版写成「每帧把电平乘 0.6」，而重画是**每 30 ms 一次** —— 等于每秒衰减 20 次。
麦克风是每 160 ms 才来一块，两块之间电平早泄光了，电平条**永远是空的**
（实测：条宽恒为 0，而 `_level_peak` 从 0.9 一路掉到 1e-6）。

**修法**：衰减按**实际经过的时间**算，不按帧算。
最终用**线性释放**（`level -= dt / 0.35`）而不是指数衰减 ——
指数永远到不了 0，会留一条**永远不消失的尾巴**（静音 1.5 秒后仍有 11% 宽的条挂着，
看着像还在收音）。线性释放正好落在 0。

### 3.2 error 状态（FR-3.6）

识别服务断连、LLM 鉴权失败这些以前**只写进日志**，用户看到的是「悬浮窗一直空着」，
完全不知道出了什么事。

**修法**：新增 `overlay.show_error(msg, auto_hide)`。
错误既进状态栏（红色「⚠️ 出错了」），也进正文区（写明具体原因 ——
状态栏只有几个字，「哪个地址、什么错」得让人看得见）。

`auto_hide` 区分两种情况：
- **独立错误**（不在录音中）→ 4 秒后自动收起
- **录音过程中出错** → **不自动隐藏**（悬浮窗正显示着流式文字，
  自动隐藏会让用户以为程序挂了）

## 五、遇到的问题

1. **`ConfigWatcher` 的竞态**：写完第一版测试是** flaky 的** ——
   10 次跑有 1 次失败。是测试写得太急还是实现有问题？
   加了 trace 才发现是实现的问题（回调被吞）。**flaky 的测试是礼物** ——
   它把一个真实的并发缺陷挖出来了。

2. **设备名匹配过于宽松会误认**：词集合判定如果只要求「有交集」，
   `"USB Mic"` 会和 `"USB Speaker"` 认成同一个设备 —— 后果是
   **把录音采到扬声器上**（用户听自己的声音，识别出一堆乱码）。
   所以要求「一方包含另一方」，并加了对应的反面用例。

3. **Tk 的 `pack_configure` 行为**：我一度以为 `pack_forget()` 之后
   `pack_configure()` 不会把控件放回来，写了个「更保险」的分支。
   实测发现 **Tk 的 `pack_configure` 会重新纳管这个控件**
   （`winfo_manager()` 变回 `"pack"`）—— 那个分支是多余的，去掉了。
   （这一条也说明：**没实测就别加「保险代码」**。）

4. **`deep_merge` 深拷贝后，我加的 json 往返保护变成冗余** ——
   配置组的 agent 已经把 `deep_merge` 改成真深拷贝了，把我这层去掉。

5. **两个 flaky 的测试断言（都是**判据太严**，不是实现有问题）**：
   全量套件连跑时暴露出来的，改完连跑多轮都稳定。

   **（1）`test_overlay_focus.py` —— 「焦点一个字都没变」判据太严**

   偶发失败时焦点跑到了 `[Chrome_WidgetWin_1] 'Cherry Studio'` ——
   那是**本会话宿主应用**（Electron）的窗口，**不是悬浮窗**。
   也就是说：别的程序在采样期间抢了焦点，那**不是悬浮窗的锅**，
   却会让用例随机变红。

   改成 FR-3.1 真正要保证的那件事：**前台/焦点从未变成悬浮窗自己**。
   抽成 `_stolen_by_overlay(fg, focus)`，并给它配了一个
   **与本环境无关**的阳性对照（直接拿悬浮窗自己的句柄喂判据，必须判成「被抢」）。
   阴性对照：把判据改成恒 `False` → 用例变红（已实测）。

   **（2）`test_overlay_states.py` —— `winfo_ismapped()` 不可靠**

   `winfo_ismapped()` 要求控件**当前**真的被映射到屏幕上，而悬浮窗是用
   Win32 的 `SetWindowPos` 显示的（**不走** Tk 的 `deiconify`）——
   Tk 内部的映射状态会滞后于实际显示，实测连跑 15 次有 1 次返回 0。

   改用 `winfo_manager()`（控件在不在布局里）—— 这正是「电平条显示/隐藏」
   这件事本身，**确定**、不依赖窗口何时被映射。
   同理，电平条宽度依赖 Canvas 算出的宽度，加了 `_wait_canvas_width()`
   等宽度就绪（宽度没算出来时 Tk 返回 1，会导致**假失败**）。

   实测：`test_overlay_states.py` 连跑 20 次 0 失败；
   `tools/run_all_tests.py`（19 个用例）连跑 3 次全绿。
