## 0. 怎么用这份计划

### 0.1 铁律

1. **没有实际运行输出 = 没做完。** 「代码写完了」不是完成，是「还没验」。
2. **每个阶段结束必须产出一份可追溯的证据**（日志文件路径 + 关键输出）。
3. **每阶段一个分支、一个 PR。** 阶段没过不合并，下一个阶段不开工。
4. **修一个缺陷配一个回归用例。** 没有用例的修复不算修（下次还会坏）。
5. **不合并就不推送。** `main` 始终保持可发布状态。

### 0.2 分支与 PR 规约

| 项 | 规约 |
|---|---|
| 分支名 | `feat/<阶段号>-<简述>`，例：`feat/s1-fix-ci`、`feat/s3-merge-engine-b` |
| 提交信息 | 中文首行说明「做了什么」，正文说「为什么」；结尾 `Co-Authored-By: Claude Code <noreply@anthropic.com>` |
| PR 标题 | `[S<n>] <一句话>`，正文写：改了什么 / 怎么验的 / 证据路径 / 关联需求编号 |
| 合并方式 | **squash merge**，保持 main 历史线性 |
| 推送时机 | 阶段内可随时推分支；**只在阶段验收通过后合并到 main** |

### 0.3 阶段依赖

```
S0 基线 ──→ S1 CI 绿 ──→ S2 严重缺陷 ──┬──→ S3 合并引擎B ──→ S4 中低缺陷
                                       │                        │
                                       │                        ↓
                                       └──────────────────→ S5 性能测量 ──→ S6 文档 ──→ S7 真机验收 ──→ S8 发版
```

**S1 必须最先做**：CI 是所有后续阶段的验收工具。CI 不绿，后面每个阶段的「自动化回归」都是空话。
