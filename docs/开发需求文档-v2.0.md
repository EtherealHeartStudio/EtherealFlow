## 0. 本版为什么重写

v1.0 是立项文档，描述的是「要做什么」。本版是**基于已发布代码的实测**重写的，描述「现在是什么、还差什么」。

审计发现三类问题，v1.0 都没预见到：

1. **14 个已验证的真缺陷**（不是猜测，每条都有复现脚本或运行证据），其中 3 个严重级：
   长语音丢 32% 内容、CI 从未成功跑过一次、Esc 取消是死代码。
2. **8 处文档说谎**：界面和 README 都声称「热词会传给识别引擎」，实际没有；
   README 三处说「大模型默认关闭」，实际代码是默认开启。
3. **需求本身有未实现的条目**：FR-1 的热键冲突处理、FR-2 的设置内设备选择、FR-3 的音量波形，
   在 v1.0 里被列为「必须实现」，但既没实现也没有测试覆盖。

v1.0 的 §9 开发计划（P1–P5）实际执行结果：**P1–P4 完成、P5 部分完成**。
本版把「已完成」从需求里移出去，只留还没做到的。

## 1. 项目概述

### 1.1 一句话

**按住热键说话，屏幕上实时看着字长出来；松开后把干净的文本注入当前输入框。**
识别与（可选的）翻译全部跑在本机，语音不出机器。

### 1.2 本轮的核心变化：两种翻译引擎

v0.3.0 的翻译走**通用 LLM**（OpenAI 兼容接口，可用本机或云端）。
EtherealLive 探索出另一条路：**Confucius4-T3PO 专训同传模型**（本机 llama.cpp，Apache-2.0）。

本轮把两者合并成**一个产品的两个可选引擎**：

| | 引擎 A：通用 LLM（v0.3.0 已有） | 引擎 B：T3PO 专模（新） |
|---|---|---|
| 部署 | 指向任意 OpenAI 兼容地址 | 本机 WSL + `llama-server`，需 9.8 GB 权重 |
| 资源 | 云端或本机小模型，几乎为零 | 纯 CPU 推理（**不占显存**），4.35 tok/s |
| 延迟 | 取决于所选模型；本机非推理模型 <1 s | 首译延迟已优化到 1.53 s |
| 质量 | 通用模型做翻译是「副作用」 | 专为同传训练，质量-延迟 Pareto 更优 |
| 术语干预 | Prompt 里塞热词 | 保留基座指令能力，术语约束是原生能力 |
| 适合 | 已有 LLM 配置的用户、云端高质量 | 追求低延迟、不愿出文本、离线 |

**设计原则：引擎 B 是可选增强，不选它的用户完全不受影响**（不下载权重、不启动额外服务、不多占任何资源）。

### 1.3 名字

产品名保持 **EtherealFlow（缥缈心流）**。GitHub 仓沿用 `EtherealHeartStudio/EtherealFlow`。
旧项目名 CherryVoice 仅作配置迁移探测保留（`client/config.py:81`）。

## 3. 系统架构

### 3.1 两段式（不变）

```
┌──────────────── Windows 客户端（Python 3.13）────────────────┐
│  全局热键 ─→ 麦克风采集 ─→ WebSocket 推 16k PCM 块            │
│                          ↓                                   │
│  悬浮窗 ←── 累积文本 ──────┘   （不抢焦点，WS_EX_NOACTIVATE）  │
│  松开 → 翻译/修正 → 文本注入当前输入框                          │
└──────────┬───────────────────────────────┬──────────────────┘
           │ ws://127.0.0.1:18300            │ ws://127.0.0.1:18400
           │ （引擎 A 路径）                  │ （引擎 B 路径，可选）
┌──────────▼──────────────┐    ┌───────────▼───────────────────┐
│ WSL · R2T2 流式 ASR      │    │ WSL · simul_server            │
│ Confucius4-R2T2 + CUDA   │───→│  取已稳定识别增量 → 喂 T3PO    │
│ 6.8 GB 显存               │    │  下发累积原文 + 只追加译文       │
└─────────────────────────┘    └───────────┬───────────────────┘
                                           │ http://127.0.0.1:8010/v1
                                ┌──────────▼───────────────────┐
                                │ Confucius4-T3PO llama-server  │
                                │ GGUF 9.8 GB · 纯 CPU           │
                                └──────────────────────────────┘
```

**为什么保持两段式**：R2T2/T3PO 的 native 后端是编译好的 Linux `.so`，Windows 侧调不了；
而热键/麦克风/悬浮窗/注入只能在 Windows 侧做。两边靠 WSL2 localhost 转发连接（实测握手 ~17 ms）。

**引擎 A 与 B 的关系**：两条路径**共用**客户端的麦克风采集、悬浮窗、注入层。
分叉点在「拿到识别文本之后」：

| 阶段 | 引擎 A | 引擎 B |
|---|---|---|
| 识别 | 客户端直连 18300 | 客户端直连 18300（simul_server 内部转发） |
| 文本显示 | 客户端渲染原文 | 客户端渲染原文（simul_server 下发累积原文） |
| 翻译 | 客户端 `translator.py` 调 LLM | simul_server 调 T3PO，下发**只追加**译文 |
| 提交 | 译文（翻译模式）或修正后文本 | 译文 |

### 3.2 模块布局（合并后）

```
EtherealFlow/
├── client/
│   ├── app.py          主编排（两种引擎在此分叉）
│   ├── asr.py          引擎 A 的识别客户端
│   ├── simul.py        引擎 B 的识别+翻译客户端        ← 从 EtherealLive 并入
│   ├── audio.py        麦克风采集          【6 模块逐字节相同，只保留一份】
│   ├── hotkey.py       全局热键            【同上】
│   ├── overlay.py      悬浮窗              【同上】
│   ├── inject.py       文本注入            【同上】
│   ├── textutil.py     文本拼接            【同上】
│   ├── win32.py        Win32 封装          【同上】
│   ├── config.py       配置
│   ├── settings_ui.py  设置界面
│   ├── llm.py          LLM 客户端（引擎 A 的修正+翻译）
│   ├── translator.py   增量翻译（引擎 A）
│   └── correction_modes.py  修正模式
├── wsl/
│   ├── r2t2_stream_server.py   识别服务
│   └── simul_server.py         同传服务（引擎 B）  ← 从 EtherealLive 并入
├── runtime/            本机运行时（模型权重不进仓）
└── scripts/            部署、启动、打包
```

**关键约束**：合并时 `win32/audio/hotkey/overlay/inject/textutil` 六个模块**只保留一份**。
EtherealLive 那边逐字节相同（已用 SHA256 核对），合并后删掉副本，避免两份实现漂移。

## 4. 前置修复需求（BF-x）—— 全部 14 条

> 每条都对应一个已验证缺陷。**每条必须配一个自动化回归用例**，用例进 `tools/run_all_tests.py`。
> 这是 v1.0 的地基：地基不牢，后面的功能都是建在流沙上。

### BF-1 【严重】长语音分段期间音频丢失

**现状**：超过 `max_utterance_sec`（默认 30 s）后轮转时丢内容。
**实测**：真实 WSL 服务 + `runtime/testdata/zh_test.wav` → 对照组 34 字，轮转组 23 字，**丢 32%**。

**根因**（四方共同作用）：
1. `client/asr.py:89-100` `rotate()` 只排 `finish`，不扣住后续音频
2. `client/asr.py:68-79` `feed()` 在轮转期间照发
3. `wsl/r2t2_stream_server.py:308-309` 收到音频时 `session is None` → **用默认参数自动开新会话**（丢 language/context）
4. `wsl/r2t2_stream_server.py:327-328` 随后的 `start` → **丢弃旧会话**，那段文本永不进 final

**要求**：
- BF-1.1 轮转期间 `feed()` 的音频进**暂存区**，不发给旧会话
- BF-1.2 新会话 `start` 之后，暂存音频**按原顺序**放回发送队列
- BF-1.3 暂存区有上限（参考 `MAX_QUEUED_BLOCKS`），超限时丢最旧并告警
- BF-1.4 服务端侧的兜底：收到 `start` 时若旧会话有音频，**先 flush 出 final 再丢弃**（双保险）

> EtherealLive 的 `client/simul.py:175-206` 已有 `_hold_audio`/`_release_hold` 实现，
> 合并时直接采用，不要重写。

**验收**：
- `tools/test_rotate_no_loss.py`：真服务对比「一次性喂完」与「中途轮转」的字数，**差值 ≤ 1 字**
- 回归用例进 `tools/run_all_tests.py`

### BF-2 【严重】CI 从未成功跑过一次

**现状**：4 个 Release 的 CI run 全部红在第一步（`UnicodeEncodeError: cp1252`）。
**已本地复现**：stdout 换成 cp1252 即崩。

**要求**：
- BF-2.1 所有输出中文的地方显式用 UTF-8（`sys.stdout.reconfigure(encoding="utf-8")` 或
  在 CI 里设 `PYTHONIOENCODING=utf-8`）—— **两个都做**，本地不设环境变量也稳
- BF-2.2 `build.yml:45` 产物自检路径改为 `build\dist\EtherealFlow\EtherealFlow.exe`
- BF-2.3 CI 触发条件覆盖 `client/** wsl/** tools/** scripts/** docs/** .github/**`
- BF-2.4 `main` 推送也触发 CI（不只是 tag 和 PR）
- BF-2.5 CI 必须跑 `test_closed_loop.py` `test_translate_flow.py` `test_stream_client.py`
  `test_mic_path.py` `test_inject_apps.py`（后两个缺依赖时明确 SKIP 并说明原因）
- BF-2.6 CI 增加一步：把 5 个关键测试的结果写进 `$GITHUB_STEP_SUMMARY`

**验收**：在 GitHub Actions 页面看到绿色对勾；故意写一个失败断言，确认 CI 变红（**阳性对照**）。

### BF-3 【严重】Esc 取消是死代码

**现状**：`client/hotkey.py:111` `self.active = False`，全仓无生产代码设成 True
（只有 `tools/test_hotkey.py:67` 设了）。两个后端的 Esc 分支都要求 `self.active`
→ **`on_cancel` 在真实使用中永不触发**。FR-1 的「录音中按 Esc 取消」根本不存在。

**要求**：
- BF-3.1 `app._on_press` 开始录音时置 `hotkey.active = True`，`_on_release`/`_on_cancel` 时置 False
- BF-3.2 取消时：停采集 → `asr.cancel_session()` → 悬浮窗提示「已取消」→ **不注入任何文本**
- BF-3.3 取消必须清掉已累积的文本（`_prefix`、`final_text`）

**验收**：`tools/test_hotkey.py` 增加生产路径断言（不手动设 `active`），
以及 `tools/test_cancel_no_inject.py` —— 取消后断言目标输入框里**没有**任何文本。

### BF-4 【中】热词从未传给识别引擎

**现状**：`client/settings_ui.py:475`、`README.md:283`、`client/config.py:62` 三处都声称传了，
实际只有 `client/app.py:151` 传了 `cfg["asr"]["context"]`（另一个独立字段），
`cfg["hotwords"]` 只流向 LLM（`app.py:194`）。

**要求**：
- BF-4.1 热词**同时**传给识别引擎（作为 context 合并进 `begin_session`）与 LLM
- BF-4.2 决定 context 的合并规则并在文档写明（建议：热词表 + 现有 context 合并，
  去重、限长，避免撑爆引擎的 context 窗口）
- BF-4.3 三处文档同步改对

**验收**：`tools/test_hotwords_reach_asr.py` —— 断言发出去的 `start` 帧里 `context` 包含热词。

### BF-5 【中】`deep_merge` 浅拷贝污染全局默认值

**现状**：`client/config.py:68-76` 返回 `dict(base)`（浅拷贝），用户配置缺失的段
直接引用 `DEFAULT_CONFIG` 的同一个对象。已验证 `merged["audio"] is DEFAULT_CONFIG["audio"]` → True。
于是 `cfg["audio"]["device"] = X` 会改掉模块级默认值。

**要求**：BF-5.1 `deep_merge` 改为真正的深拷贝（递归复制 dict/list）。

**验收**：`tools/test_config.py` —— 加载配置后修改某个段，断言 `DEFAULT_CONFIG` 未被影响。

### BF-6 【中】配置无类型校验，坏配置崩在启动

**现状**：`config.py:135-142` 只处理「JSON 解析失败」。合法 JSON 但类型错的配置会一路传到
`overlay.py:93` 抛 `TypeError`，或 `hotkey.py:79` 抛 `ValueError` → **启动崩溃**。
且损坏的配置被**静默丢弃并用默认值覆盖** → 用户的 API Key 和热词没了。

**要求**：
- BF-6.1 加载后逐字段做类型/取值校验，**不合法就回退该字段的默认值**，不崩
- BF-6.2 回退时**保留用户原文件**（备份成 `config.json.bak`），并在日志里说明
- BF-6.3 设置界面显示「有 N 项配置无效，已回退默认值」，让用户知道

**验收**：`tools/test_config.py` —— 喂各种坏配置，断言不崩 + 坏字段被回退 + 原文件被保留。

### BF-7 【中】LLM 地址格式错误会杀掉修正线程

**现状**：`client/llm.py:344-372` 的 `except` 覆盖 `URLError`/`OSError`/`socket.timeout`，
但 `http://host:abc/v1` 抛 `http.client.InvalidURL` —— **既不是 URLError 也不是 OSError**，
直接逃逸出 `_run` → 逃逸出 `correct` → 杀掉 `app.py:194` 的线程。
**结果：不注入任何东西，`done` 状态永不设置，UI 永远停在「修正中」。**

**要求**：
- BF-7.1 `except` 覆盖 `http.client.HTTPException`（含 `InvalidURL`）与 `ValueError`
- BF-7.2 地址在**发请求前**先做格式校验，格式非法直接归类为「配置错误」并提示用户
- BF-7.3 任何异常都不得逃逸出 `correct`/`translate` —— **保证一定有文本被注入**

**验收**：`tools/test_llm.py` 增加「畸形 URL」用例，断言抛出的是 `LlmError` 子类且
`Outcome.text` 等于原文。

### BF-8 【中】自检断言恒真

**现状**：
- `tools/test_llm.py:295-298`：`ok = (A and B and C and D and E) or want_changed`
  Python 优先级下等价于 `((...) or want_changed)`，凡是 `want_changed=True` 的行**恒为真**
- `tools/test_translator.py:135`：`sent == "".join(dict.fromkeys([sent]))` 对**任意字符串**恒真

**要求**：BF-8.1 修正优先级（加括号），让每个断言真的能失败；
BF-8.2 补一条「阳性对照」：故意让 fake 服务返回坏输出，断言用例**必须失败**。

**验收**：BF-8.2 的反向验证 —— 人为破坏一处实现，用例必须变红。

### BF-9 【中】注入成功与否是盲的

**现状**：
- `client/inject.py:297` `press_ctrl_v()` 的 `SendInput` 返回值被忽略，`:299` 无条件 `res.ok = True`
  → **UIPI 阻止注入时（目标是管理员应用）报成功但什么也没输入**
- `:294-295` 剪贴板回读不一致时只警告，**照样粘贴**（可能粘到旧内容）
- `:318` 剪贴板还原失败**完全静默**
- `app.py:230` 在 `inject()` 返回后立刻打日志，而还原发生在 500 ms 后 → **日志里永远看不到「剪贴板已还原」**
- `inject.py:149-150` `has_other` 不含 `CF_BITMAP`/`CF_DIB`/`CF_DIBV5` → **纯图片剪贴板被静默销毁**

**要求**：
- BF-9.1 检查 `SendInput` 返回值：为 0 则判定失败，写进 `InjectResult`
- BF-9.2 剪贴板回读不一致时**不粘贴**，改走逐字键入
- BF-9.3 还原失败要进 `InjectResult.warnings`，且日志要等还原完成后再打
- BF-9.4 `has_other` 覆盖全部剪贴板格式（含位图）；检测到非文本就**自动改用逐字键入**，
  绝不 `EmptyClipboard` 销毁用户数据
- BF-9.5 `InjectResult` 从 `ok: bool` 升级为**三态**：`delivered` / `unconfirmed` / `not_applied`
  （借鉴 typeflux 的 `TextDeliveryResult`）

**验收**：`tools/test_injection.py` 增加「SendInput 返回 0」「回读不一致」「图片剪贴板」三个用例；
`test_inject_apps.py` 的判定改用三态。

### BF-10 【中】翻译方向逐段判断，一句话被劈成两种语言

**现状**：`client/translator.py:222-224` 每段独立调 `guess_target_language`（数 CJK vs 拉丁字符）。

### BF-15 【严重·S1 新发现】悬浮窗在创建/显示时抢走前台与键盘焦点

> **这是 2026-10-24 做 S1（修 CI）时新发现的**，不在最初的 14 条里。
> 严重度等同 BF-1：**它让产品「说了话，但什么都没进去」**。

**症状**：`tools/test_closed_loop.py` 稳定报「前台是悬浮窗自己（0x…），跳过注入以免误伤」，
目标文本框始终是空的。识别、LLM 修正都正常，只有最后一步注入被跳过。

**根因**（四层叠加，逐层修掉）：

| # | 原因 | 证据 |
|---|---|---|
| 1 | `overrideredirect(True)` 之后 **`GetAncestor(GA_ROOT)` 失效**，返回 TkChild 自己而不是真正的 TkTopLevel → `WS_EX_NOACTIVATE` 加错了窗口 | `client/win32.py:top_level_window` 改用 `GetParent` 链 |
| 2 | `WS_EX_NOACTIVATE` 加得**太晚**（`update_idletasks()` 之后），而 Tk 首次映射窗口时 Windows 必然激活它 | `client/overlay.py:_build` 调整顺序 |
| 3 | `attributes("-topmost", True)` 会触发窗口**重新激活** | 移到样式设置之后 |
| 4 | `show_without_activating` 里 **`ShowWindow` 排在 `SetWindowPos(SWP_NOACTIVATE)` 前面** —— 对隐藏窗口，ShowWindow 会先激活再显示 | `client/win32.py:show_without_activating` 调换顺序 |

**要求**：
- BF-15.1 顶层窗口解析改用 `GetParent` 链（`GA_ROOT` 只作兜底）
- BF-15.2 `WS_EX_NOACTIVATE` 在窗口映射前加好
- BF-15.3 `-topmost` 在样式设置**之后**设
- BF-15.4 `show_without_activating` 先 `SetWindowPos(SWP_NOACTIVATE)` 再 `ShowWindow(SW_SHOWNOACTIVATE)`
- BF-15.5 加**兜底**：显示前记下前台窗口与键盘焦点，显示后若被夺走就还回去
  （跨线程 `SetFocus` 需要 `AttachThreadInput`，本机实测会被系统拒绝，
  所以它只是兜底，不是保证）
- BF-15.6 `client/win32.py` 新增 `set_focus_across_threads()`、`set_noactivate_style()`；
  `GetParent`/`SetFocus`/`IsWindow` 补齐 ctypes 签名（64 位句柄截断坑）

**验收**：
- `tools/test_closed_loop.py` **端到端通过**（识别 → 修正 → 文本进目标框）
- `tools/test_overlay_focus.py` 9 项全过（阳性对照在本机会因前台锁太紧而 SKIP，
  属环境限制，测试自己会写明「未被阳性验证」）
- 对照实验脚本留在仓库里：`tools/repro/overlay_focus_timing.py`（时序对照）、
  `tools/repro/overlay_focus_diag.py`（句柄与样式诊断）

**已修复**（2026-10-24，见 S1 提交）。

## 8. 风险与对策

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| 1 | 合并时六个共享模块出现两份实现 | 两边行为漂移，bug 修一边漏一边 | 合并时**只保留一份**，删副本；合并后跑一遍全部用例 |
| 2 | 引擎 B 权重 9.8 GB，下载门槛高 | 用户装不上 | 引擎 B 是可选增强；不选完全不影响；提供下载脚本 + SHA256 |
| 3 | 引擎 B 纯 CPU，实测 1.17–1.5× 实时 | 说 10 秒要等 12–15 秒 | 明确写进 README 的「已知限制」；引擎 A 仍是一等公民 |
| 4 | 真机验收依赖舰长本人 | 排期受人力约束 | 清单先给，验收可与开发并行；开发不依赖验收结果启动 |
| 5 | 本机 8 GB 显存是硬约束 | 引擎 B 走 CPU 是唯一选择 | 不追求 GPU 卸载（需 sudo 与 CUDA 工具链）；性能目标按 CPU 现实定 |
| 6 | 修了 14 个缺陷，可能引入回归 | 老问题复发 | 每个修复配回归用例；全部进 CI；合并前跑全量 |
| 7 | 文档修正涉及 20+ 处 | 改漏 | 建核对表 D-1..D-5，逐条打勾，不靠记忆 |
| 8 | CI 触发条件扩大后跑得慢 | 反馈变慢 | 区分「快速检查」与「完整检查」两个 job |
